* Motivation

Futhark is a pure, functional array programming language. It has no notion of
memory or resources, so it is entirely up to the compiler to transform the
programs written by users into something that maps to the physical reality,
including supporting a notion of memory.

#+name: and_plus_one
#+caption: A simple futhark function.
#+begin_src futhark -n -r -l "-- ref:%s"
  entry and_plus_one (xs: *[]i32): *[](i32, i32) =
    map (\x -> (x, x + 1)) xs
#+end_src

As a short example, consider the ~and_plus_one~ function shown in figure
[[and_plus_one]]. Each element of the input array is turned into a pair containing
the original value and its successor. During compilation, the Futhark compiler
will insert memory and turn it into the code shown in figure [[and_plus_one_kernelsmem]].

We can see the memory allocations inserted by the compiler on lines
[[(and_plus_one_kernelsmem_alloc_1)]] and [[(and_plus_one_kernelsmem_alloc_2)]]. For the
most part, Futhark does not currently attempt to optimize these memory
allocations in any way, but merely inserts them where necessary.

It is important to mention here, that the allocations shown above do not
necessarily translate into actual on-device allocations. Futhark statically
determines which allocations are needed, but the compiled program additionally
contains a dynamic memory allocator, which can reuse already allocated memory if
it has been freed. The result is that the statically determined memory usage
constitutes an upper bound of the actual memory usage.

When using Futhark, we are most often trying to make something run fast on a
GPU. Physical allocations, meaning that the dynamic allocator does not have any
appropriate memory blocks it can reuse, take time. So reducing the number of
such allocations is the most obvious benefit of reducing memory usage of Futhark
programs.

Each allocation inserted by the Futhark compiler also potentially uses up
valuable memory on the GPU. By reducing the memory usage, we enable more
programs to run on the GPU. For instance, many programs benefit from intra-group
parallelism and using shared memory to reduce the number of global memory
acccesses (which are slow). However, the amount of shared memory on GPUs can be
quite limited. If we can statically determine a lower bound on the shared memory
needed, we can some programs will be safely able to run with larger datasets
than before.

Copies may not seem directly related to allocations, but if we can statically
merge some memory blocks, that will allow us to reduce the number of copies in
some programs. Consider again the ~and_plus_one~ function in figure
[[and_plus_one]]: The input array is consumed by the function, so it or its aliases
cannot be used anywhere else. Furthermore, ~xs~ is used nowhere besides as an
argument to map. Therefore, instead of allocating a new memory block for the
first result of the entry (which is really just the input), we should be to
reuse ~xs_mem_4071~ /and/ get rid of the copy on line
[[(and_plus_one_kernelsmem_copy)]].

* LUD

Unfortunately, there are many benchmarks for which the optimization techniques
in ReuseAllocations is too simplistic. One such benchmark is the [[file:~/src/futhark-benchmarks/rodinia/lud/lud.fut][LUD]]
benchmark. LUD computes the LU-decomposition of a matrix. The bulk of the code
is made up by four functions: ~lud_diagonal~, ~lud_internal~,
~lud_perimeter_upper~ and ~lud_perimeter_lower~, of which the two latter are
almost identical.

#+name: lud_perimeter_upper
#+caption: Futhark code for ~lud_perimeter_upper~.
#+begin_src futhark -n -r -l "-- ref:%s"
  let lud_perimeter_upper [m][b] (diag: [b][b]f32, a0s: [m][b][b]f32): *[m][b][b]f32 =
      let a1s = map transpose a0s in
      let a2s =
          map  (\a1: [b][b]f32 ->
                map  (\row0: [b]f32 ->                     -- ref:lud-upper-inner-map
                      loop row = copy row0 for i < b do       -- ref:lud-upper-l2
                      let sum = loop sum=0.0f32 for k < i do  -- ref:lud-upper-l1
                                  sum + diag[i,k] * row[k]    -- ref:lud-upper-s1
                      let row[i] = row[i] - sum               -- ref:lud-upper-s2
                      in  row
                     ) a1
               ) a1s
      in map transpose a2s
#+end_src

Let's take a look at ~lud_perimeter_upper~, as shown in figure
[[lud_perimeter_upper]]. It takes an $b \times b$ matrix ~diag~ and a list of $m$ $b
\times b$ matrices a0s. The inner map, starting on line [[(lud-upper-inner-map)]],
processes the rows of a given matrix: Each element is processed in sequence by
multiplying all the updated earlier elements with the row elements of
~diag~. Interestingly, this could be done entirely in-place, because updating
element $k$ of ~row~ only depends on updated elements with index less than $k$.

The question is, how can we teach Futhark to recognize a pattern such as this,
and optimise it to do the updates in-place? Inspired by cite:oancea-2012-logic,
let's try to summarize the accesses of the innermost map.

The access of $row[k]$ on line [[(lud-upper-s1)]] accesses $a1s[M b^2 + N b + k]$,
where $M$ and $N$ are some indices into the $a1s$ and $a1$ arrays as given by
the maps. Aggregating the accesses over the loop on line [[(lud-upper-l1)]] gives us
the LMAD $[1] \vee [i] + M b^2 + N b$, which states that the loop accesses with
a step of one, a span of $i$ and an offset of $M b^2 + N b$. Aggregating over
the outer loop on line [[(lud-upper-l2)]] gives us $[1] \vee [b] + M b^2 + N b$,
while the two outer maps leaves us at $[1, b, b^2] \vee [b, b^2, b^2m] + 0$.
There are two accesses on line [[(lud-upper-s2)]], a read and a write. Both are both
described by the same LMAD as the previous read.

The question is now, what can we do with this? The technique described in
cite:oancea-2012-logic puts these accesses into three different sets: ReadOnly,
WriteFirst and ReadWrite, and the accesses in ~lud_perimeter_upper~ all come out
as ReadWrite. For our goal of reusing the memory blocks, however, that's not
really helpful, as ReadWrite does not guarantee that the contents are not read
after the write.

* NW

The [[file:~/src/futhark-benchmarks/rodinia/nw/nw.fut][NW]] benchmark is parallel implementation of the Needleman-Wunsch algorithm, a
dynamic programming algorithm for comparing DNA sequences. The basic algorithm
works by iteratively updating a matrix, with each value depending on the result
of the results to the top, left and top-left. Parallelism is achieved by working
on anti-diagonal blocks that are independent of each other. In its current
incarnation, it has some unnecessary allocations: all results are first written
to an intermediary value inside ~intraBlockPar~, and only afterwards are they
written into the result matrix. However, since all accesses below and to the
right of the first row and column are strictly WriteFirst, and because the main
function consumes its argument, it should be possible to do the entire algorithm
in-place. But how do we teach the compiler this?
